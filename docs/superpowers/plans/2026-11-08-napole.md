# Napole Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A scheduled entry-step processor, `Processor.Napole`, that counts how a watched workflow's
executions imported in the last window ended (Failed / Cancelled / Complete), from Elasticsearch
logs, and sends one hermetic count report per tick to a kafka-exporter.

**Architecture:** A pure core with three parts: the window arithmetic, the verdict rules, and the
report builder. Around it sit an ES|QL trail source over HTTP (two statements per tick) and a thin
`BaseProcessor<NapoleConfig>` that wires clock → window → source → verdicts → report → send.
Shaped after `Processor.Analyst`: an entry step that opens its own lineage and reads ES.

**Tech Stack:** .NET 8, `BaseProcessor.Core` 1.0.0 (package), `Microsoft.Extensions.Http`, xUnit +
NSubstitute + `Microsoft.Extensions.Time.Testing`, Elasticsearch 9.3 ES|QL `_query` with named
params, Kubernetes (kind), Kafka 3.9.1 container `skp-kafka`.

**Spec:** `docs/superpowers/specs/2026-11-08-napole-design.md`. Read it. This plan argues from it.

## Global Constraints

- Branch `feature/napole`, cut from `feature/ems-exporter` HEAD, **not** `main`: that branch is 80
  commits ahead of `main` and carries the importer and exporter behaviour Napole reads.
- Step payload has **exactly two** fields: `watchedWorkflowId` (Guid, required), `windowMinutes` (int ≥ 1, required).
- Everything else is pod configuration under section `Napole`: `ElasticBaseUrl` (required),
  `LagSeconds` (default 60), `TrailMinutes` (default 10), and `Report:ReporterComponentName`,
  `Report:ReporterSubComponentName`, `Report:ReporterNetworkName`, `Report:SrcCode`,
  `Report:SagCode` (all required). A missing required option fails the pod **at startup**.
- Report JSON field names verbatim, misspellings included: `commonDimentions`,
  `mandatoryMeasurments`, `timStampHour`. Every time is epoch milliseconds, as a number.
  `timStampHour` = the UTC hour of `reportFromTime` as the number `YYYYMMDDHH`.
- Counts are per execution, and only executions whose round trip terminated count:
  `outputCount + failedCount + discardedCount == inputCount`, asserted before sending.
- Nothing terminated in the window → throw `CancelledException`. **Never** return without sending
  (the framework reports that as Failed).
- Index `logs-generic.otel-default`. Every query is filtered by
  `attributes.WorkflowId == watchedWorkflowId`, posted to `/_query?allow_partial_results=false`.
- Window: `to = floor_UTC(now − lag, windowMinutes)` on the epoch grid; `from = to − windowMinutes`;
  trail span `[from − trail, to + trail)`.
- Code style: match the repo. Long `///` doc comments explain *why*, `ConfigureAwait(false)`, file-scoped
  namespaces, `TreatWarningsAsErrors` (from Directory.Build.props). Never declare package versions
  in the csproj.
- Tests: build with `dotnet build src/tests/BaseApi.Tests`, run with
  `dotnet src/tests/BaseApi.Tests/bin/Debug/net8.0/BaseApi.Tests.dll --filter-class "<Namespace.Class>"`.
  The runner is MTP, so `dotnet test --filter` is ignored. **Schema-backed tests** (anything calling
  `ProcessorJsonSchemaValidator` / `ConfigSchemaConformance`) are blocked on this machine by Windows
  Application Control (`JsonSchema.Net.dll`, FileLoadException 0x800711C7). Run those in the container:
  ```bash
  MSYS_NO_PATHCONV=1 docker run --rm -v "C:/Users/katan/source/repos/SK_P11:/ro:ro" mcr.microsoft.com/dotnet/sdk:8.0-bookworm-slim bash -c \
  ```

## Review Focus

1. **A run that fans out with one branch still open** must not count as Complete. Pinned in Task 3 (`AFanOutWithOneOpenBranchIsUnfinished`) and checked live in Task 5 (`openBranches`).
2. **An ES answer cut short** (`is_partial`, or a statement returning exactly its `LIMIT` rows) must fail the tick, never send smaller counts. Pinned in Task 4.
3. **A tick that runs late**, e.g. 10:59:59 on a 10-minute grid with a 60 s lag, must still report the 10:40–10:50 slot. Pinned in Task 2 (`ALateTickStillReportsItsGridSlot`).
4. **`timStampHour` across a UTC day boundary**, where `from` = 2026-12-31T23:50Z must give `2026123123`, in UTC whatever the pod's local zone. Pinned in Task 3.
5. **The log template prefixes** (`handed off`, `the step returned`) are log text, not a contract. If anyone rewords them, Napole miscounts with no error. Covered only by the live check in Task 6. Name them once, as constants, in `TrailRecords.cs` (Task 4), with a comment saying which emitter writes each.

- Produces: `internal static class TrailRecords` with `const string Index = "logs-generic.otel-default"`, `HandedOff = "handed off"` (emitted by the Orchestrator's dispatch path), `StepReturned = "the step returned"` (`BaseProcessor.Core` `ProcessDispatchHandler`), and `const int RowLimit = 10_000`.

The two statements are fixed copy, verified against the live cluster on 2026-11-08: for 10:40–10:50 they return 80 ids → 48 Failed / 16 Cancelled / 16 Complete, 0 open branches. Build them from `TrailRecords` constants, and post each as `{"query": ..., "params": [{"workflow": "<guid>"}, {"from": "<iso>"}, {"to": "<iso>"}]}`. ISO strings are `yyyy-MM-ddTHH:mm:ss.fffZ`, UTC.

```
-- A: the executions this tick owns
FROM logs-generic.otel-default
| WHERE resource.attributes.service.name == "kafka-importer" AND attributes.Record IS NOT NULL
  AND attributes.WorkflowId == ?workflow AND @timestamp >= ?from AND @timestamp < ?to
| STATS BY attributes.ExecutionId
| LIMIT 10000

-- B: their trails; params workflow, trailFrom, trailTo; the IN list is spliced, from Guid.ToString("D") only
FROM logs-generic.otel-default
| WHERE attributes.WorkflowId == ?workflow AND attributes.ExecutionId IN (<ids>)
  AND @timestamp >= ?trailFrom AND @timestamp < ?trailTo
| EVAL svc = resource.attributes.service.name, fmt = TO_STRING(`attributes.{OriginalFormat}`)
| EVAL isImport = CASE(svc == "kafka-importer" AND attributes.Record IS NOT NULL, 1, 0),
       isHandoff = CASE(svc == "orchestrator" AND STARTS_WITH(fmt, "handed off"), 1, 0),
       isReturn = CASE(svc != "orchestrator" AND STARTS_WITH(fmt, "the step returned"), 1, 0),
       isTerminal = CASE(attributes.StepRole == "terminal", 1, 0),
       isFailed = CASE(svc == "orchestrator" AND attributes.Result == "Failed", 1, 0),
       isCancelled = CASE(svc == "orchestrator" AND attributes.Result == "Cancelled", 1, 0)
| EVAL branch = CASE(isHandoff == 1, attributes.NextEntryId, isReturn == 1, attributes.EntryId, "-")
| STATS imports = SUM(isImport), terminals = SUM(isTerminal), failed = SUM(isFailed), cancelled = SUM(isCancelled),
        handedOff = MAX(isHandoff), returned = MAX(isReturn) BY attributes.ExecutionId, branch
| STATS imports = SUM(imports), terminals = SUM(terminals), failed = SUM(failed), cancelled = SUM(cancelled),
        openBranches = SUM(CASE(branch != "-" AND handedOff == 1 AND returned == 0, 1, 0)) BY attributes.ExecutionId
| LIMIT 10000
```

This is two statements, not the spec §4.3's three: the Failed/Cancelled outcomes fold into B as
counts, because the report needs no reasons or step names. If statement A returns no ids, statement B
is not sent.
