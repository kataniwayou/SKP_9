What the drawing can't show you

4b runs after 4, not beside it

AlphaBeta lifts the XML Acme has already rendered, so it carries PreviousCompleted and an Acme failure skips it. A parallel branch off the expander would redo the whole provider mapping — and would still run after its sibling had failed.

The cancel is in the handler, not in the graph

Acme gates the artist on a whitelist projected into L2 at the address its payload names — skp:1a56b3ca…:cache:chain-artists, written when the workflow starts and deleted when it stops. An artist that is not on the list, or no artist at all, ends the branch as Cancelled: an unapproved document is one this chain is not meant to carry, not one it could not read. Nothing in the API rows says this can happen — the outcome exists only in AcmeHandler.Augment, which is why the stub is drawn from the source and not from the graph. Only Acme reads a list; 4b carries no cacheAddress and needs none.

An empty whitelist and a missing one are different failures

A root projected as [] is a list that approves nobody and cancels each document. A root that was never projected — the workflow names no such cache, or the address is a typo — is a Failed step saying so. The writer stores the empty dictionary explicitly to keep those two apart, since in the logs they otherwise read identically.

The two XMLs are one document

4b renders nothing: it passes Acme's bytes through untouched. Verified live — the standalone track01.xml is sha256-identical to the copy inside the zip. Not "kept in step with"; the same bytes.

Seven of eight schema edges are enforced again

The four ids nulled on 2026-09-14 — sk-normalizer on both sides, the collapser's and the persister's inputs — were restored the same day, and the drawing's gate dots follow. The one still open is the last: kafka-exporter declares no input schema, so nothing checks what the persister hands it. The normalizer's input is forced to equal its own output, because SchemaEdgeValidator compares row ids and 4b's parent is 4 — the same row. A tighter input is refused even when its definition is byte-identical.

The stored description is two features stale

The workflow row still reads “KafkaImporter → FileFetcher → ArchiveExpander → ArchiveCollapser → FilePersister → KafkaExporter”. It has never mentioned sk-normalizer, added at hop 4, nor the AlphaBeta fork, nor the cache the workflow now names. The steps above are the truth.

track01.xml is not one file per run

The zip carries a guid, so each run adds one. The xml takes the basename from inside the bundle — track01 in every fixture — and the persister overwrites deliberately so re-runs are idempotent. Many zips, one xml.

A multi-pair bundle splits the branches

Acme has a container to hold both items; 4b's leaf root holds one file, so it fails by name rather than dropping the second silently. That failure takes the record-outcome edge like any other.
